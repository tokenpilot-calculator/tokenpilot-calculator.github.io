PRACTICAL PROMPT GUIDE

Build a playable game feature — not just a menu or mockup.

Game-building prompts often ask for too much at once. A better task describes the current project, one gameplay outcome, its states and constraints, and how to test it in the running game. Use this template to keep changes playable and easier to debug.

Details that make a game-development prompt usable

Game features depend on input, state, camera, collision, animation, UI, and persistence. Name the parts relevant to the feature and ask the assistant to inspect how the project connects them.

01

One player-facing outcome

Describe one mechanic: a dash, inventory slot, enemy behavior, or daily reward. Split larger ideas into separate build steps.

02

Engine and current state

Name the engine and version, language, scene or page, and what already works. Ask the agent to inspect project files before changing architecture.

03

Rules and states

Define what starts the mechanic, what can interrupt it, and what happens on success, failure, or reset.

04

Controls and feedback

Specify input, animation, sound, HUD feedback, and mobile controls where relevant.

05

World integration

Call out collision, camera movement, coordinate space, scene objects, save data, or multiplayer rules when they affect the task.

06

Playable verification

Require the feature to be tried in the running game. A static screenshot or menu alone does not verify an interactive mechanic.

A vague game request vs. a testable one

Specific steps make the result easier to reproduce and verify.

Too vague

“Make my game better and add cool combat.”

Better

“In the existing 2D platformer, add a short dash on Shift. It lasts 180 ms, has a 650 ms cooldown, stops at solid walls, plays the existing dash animation, and is disabled while paused. Test against a wall, while airborne, during pause, and after respawn. Preserve jump and attack controls.”

Copyable game-development prompt

Implement one playable feature in the existing game project.

PROJECT:
[Engine/version or web stack, genre, perspective, current scene/page, and existing behavior.]

FEATURE:
[Describe one specific player-facing outcome.]

GAMEPLAY RULES:
- Trigger/input: [what starts the mechanic]
- State and duration: [what changes and for how long]
- Limits/interruption: [cooldown, collision, pause, failure, or cancel states]
- Feedback: [animation, sound, UI, effect, or message]

PRESERVE:
[Existing controls, movement, saves, progression, camera, art direction, and systems that must not regress.]

CONSTRAINTS:
- Inspect the project structure and relevant scripts/scenes before editing.
- Integrate with existing systems rather than duplicating input, state, or UI systems.
- Keep gameplay objects and collision data as real scene objects/components where interaction depends on them; do not replace them with a flat background image.
- Avoid unrelated refactors and new dependencies.

PLAYTEST / ACCEPTANCE:
- Run the game or the closest available interactive environment.
- Test the normal path, a boundary case, and an interruption/reset case.
- Check input, camera, collision, animation, and persistence where relevant.
- Report changed files, what was tested in the running game, and any unverified behavior. Do not claim a playtest happened if it did not.

Game-feature review checklist

  • Is the request limited to a feature that can be tested independently?
  • Did you define the trigger, states, limits, and reset behavior?
  • Have you named systems that must remain working?
  • Does the task require collision, camera, animation, or persistence?
  • Did you ask for a playtest instead of only a screenshot?

Game-development prompt questions

Should I ask AI to build the whole game at once?

For the first playable version, keep the scope small: one scene, one main loop, and a few mechanics. Add systems in testable increments.

Why mention collision and camera behavior?

If movement or interaction depends on them, a visually plausible result can still be unplayable without correct collision and camera logic.

What if AI cannot run my game?

Ask it to say so explicitly, inspect available files and tests, and give manual playtest steps. Do not treat unrun tests as passed.
