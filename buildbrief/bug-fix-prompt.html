Write a bug-fix prompt that asks for the cause, not just a patch.

Vague bug reports invite guesses. A useful AI coding task describes what happened, what should have happened, how to reproduce it, and what must remain unchanged. This guide gives you a reusable prompt and a checklist for making the next fix easier to review.

What a strong bug-fix request includes

Give the coding assistant evidence it can inspect. You do not need perfect technical language; clear symptoms are more useful than a long, unfocused explanation.

01

Observed result

State the exact wrong behavior, visible error, or unexpected output. Avoid guessing the cause before it is investigated.

02

Reproduction steps

Write the shortest sequence that triggers the problem: page, action, input, and result.

03

Expected result

Describe the behavior a user should see. That turns “fix it” into a testable goal.

04

Project context

Name the framework, device or browser, related files, and the smallest useful error snippet when known.

05

Boundaries

Ask for a targeted patch. Preserve unrelated behavior, existing data, public interfaces, and current design.

06

Verification

Require a relevant test or reproducible check, plus a summary of modified files and remaining manual tests.

A vague request vs. a useful one

Specific steps make the result easier to reproduce and verify.

Too vague

“The save button is broken. Fix it.”

Better

“On mobile, open Settings, change the display name, and press Save. The button shows success, but after reloading the page the old name returns. Find the root cause, change only the responsible code, and verify that the new value persists without breaking desktop saving.”

Copyable bug-fix prompt

Investigate and fix the bug described below.

BUG / SYMPTOM:
[Describe the incorrect behavior and exact error message, if any.]

REPRODUCTION STEPS:
1. [Starting page or state]
2. [Action and input]
3. [Actual result]

EXPECTED RESULT:
[Describe what should happen instead.]

PROJECT CONTEXT:
[Framework, browser/device, relevant files, logs, or recent changes.]

CONSTRAINTS:
- Inspect the relevant code and evidence before editing.
- Identify the likely root cause; do not hide the symptom with an unrelated workaround.
- Make the smallest safe change that fixes the cause.
- Preserve unrelated features, stored data, public interfaces, and current design.
- Do not add dependencies without a clear need; explain first if one is needed.

VERIFICATION:
- Run the most relevant available test or command.
- Check the original reproduction steps and one nearby regression scenario.
- Report changed files, root cause, checks run, and anything that still needs manual testing.
- Do not claim a test passed unless it was actually run.

Before you send the prompt

  • Can another person reproduce the bug from your steps?
  • Did you distinguish actual behavior from expected behavior?
  • Did you include the real error text instead of paraphrasing it?
  • Did you limit the scope and name what must not change?
  • Did you request a test tied to the reported failure?

Bug-fix prompt questions

Should I paste the whole codebase?

Usually not. Start with reproduction steps, error output, and the relevant file or function. An agent with repository access can inspect additional context when needed.

Should AI edit files immediately?

For a risky or unclear bug, ask it to inspect and explain the likely cause first. Even for a small issue, require verification after the patch.

Can a prompt guarantee a fix?

No. It improves clarity, but you should inspect the diff and test the original failure in the real project.
